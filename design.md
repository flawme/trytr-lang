# 2D Visual Document Language
## Working Technical Specification — Version 0.1

**Status:** Architecture and design decisions consolidated
**Implementation language:** C23
**Execution model:** Interpreter-first
**Primary purpose:** AI-generated visual content and universal documents
**Rendering domain:** Strictly 2D
**Runtime strategy:** Minimal mandatory core with modular capabilities

---

# 1. Vision and purpose

The language is designed to provide one unified representation for visual documents generated by AI systems and human authors.

It replaces the need to combine unrelated formats and technologies for ordinary document rendering, including separate markup, mathematics, charting, diagramming and graphics systems.

The language should be capable of representing:

- Rich text and structured documents.
- Mathematical equations and scientific notation.
- Tables and structured datasets.
- Charts and scientific graphs.
- Electronic circuit diagrams and flowcharts.
- Vector illustrations and technical drawings.
- Raster and vector images.
- Presentations and educational documents.
- Interactive scientific and educational content.
- Screen-oriented and print-oriented documents.

The language is declarative rather than general-purpose.

Its primary job is to describe **what a document contains and how it should be presented**, not to provide an unrestricted programming environment.

## 1.1 Fundamental design goals

1. Small and efficient mandatory runtime.
2. Strict syntax and predictable interpretation.
3. Safe parsing of untrusted AI-generated documents.
4. Advanced 2D drawing capabilities.
5. Cross-platform consistency.
6. Incremental rendering and streaming.
7. Typed mathematics and scientific calculations.
8. Unified document representation.
9. Extensibility without bloating the core.
10. Deterministic behavior wherever practical.

## 1.2 Explicit non-goals

The language is not intended to:

- Replace HTML, CSS or JavaScript as general web technologies.
- Become a general-purpose programming language.
- Become an application development framework.
- Support unrestricted executable scripts.
- Support native 3D scenes, meshes, cameras or lighting.
- Automatically access arbitrary files or networks.
- Provide unlimited computation.

Pre-rendered images of 3D content may be included as ordinary raster images.

# 2. Overall architecture

The language uses a shared document model and a compact execution representation.

## 2.1 Processing pipeline

Source documents pass through the following stages:

1. Source reader.
2. Lexer.
3. Parser.
4. Syntax validation.
5. Type and semantic validation.
6. Resource and capability validation.
7. Document AST construction.
8. Compact instruction IR generation.
9. Bounded interpreter VM.
10. Dependency tracking and scheduling.
11. Layout and rendering.
12. Platform-specific output backend.

The pipeline is:

Source → Parser → Validator → AST/IR → VM → Layout → Renderer → Output

This is not a traditional native-code compilation pipeline.

The source is translated into an optimized intermediate representation that the interpreter executes.

## 2.2 Abstract syntax tree and execution IR

The architecture uses two related representations.

**Document AST**

Preserves:
- Document hierarchy.
- Element types.
- Semantic information.
- Properties.
- Identifiers.
- Layout relationships.
- Resource references.

**Compact execution IR**

Contains:
- Validated operations.
- Typed operands.
- Resource references.
- Rendering instructions.
- Expression operations.
- Dependency information.

The AST remains the semantic source of truth. The IR is an optimized representation for execution.

## 2.3 Interpreter requirements

The interpreter must be:

- Deterministic within specified numerical and rendering tolerances.
- Bounded in memory and execution time.
- Capable of partial document execution.
- Incremental.
- Independent of arbitrary operating-system access.
- Compatible with single-threaded execution.

There is no requirement for JIT compilation or native machine-code generation.

# 3. Language syntax

## 3.1 Syntax philosophy

The syntax combines readable text with explicit rendering constructs.

Ordinary text should not require an explicit text keyword.

Special elements use explicit declarations.

The source format must be compact enough for AI generation but readable enough for manual editing.

## 3.2 Structural rules

- Explicit braces `{}` define blocks.
- Structural parsing does not depend on indentation.
- Whitespace is generally insignificant between structural tokens.
- Named properties are the default.
- Positional shorthand is permitted for selected common elements.
- Strings and identifiers have explicit interpretation.
- Unknown properties and invalid arguments produce diagnostics.
- No silent syntax correction.

## 3.3 Illustrative source

The following is an illustrative syntax proposal, not the finalized formal grammar:

```text
@document(version: 1) {
    @heading #title {
        JFET Characteristics
    }

    @math #equation1 {
        I_D = I_{DSS}(1 - V_{GS}/V_P)^2
    }

    @rect(10, 20, 100, 50)

    @text {
        The output characteristic of an N-channel JFET.
    }
}
```

The exact tokenization and grammar productions will be defined separately.

## 3.4 Properties

Named properties are preferred:

```text
@rect {
    x: 10
    y: 20
    width: 100
    height: 50
}
```

Positional shorthand is allowed only when the element's schema defines an exact argument order.

There must be no ambiguous positional interpretation.

## 3.5 Comments and metadata

The source language supports:

- Single-line comments.
- Multiline comments.
- Document metadata.
- Optional annotations.

Comments do not affect document rendering.

Binary documents may omit comments unless source preservation is requested.

# 4. Type system

The language is fully typed.

Every element, property, expression and resource reference must have a defined type.

The runtime must not guess what a value means.

## 4.1 Fundamental type categories

Expected types include:

- Boolean.
- Integer.
- Floating point.
- Decimal.
- Fixed point.
- String.
- Color.
- Length.
- Angle.
- Duration.
- Physical quantity.
- Vector.
- Matrix.
- Complex number.
- Dataset.
- Resource reference.
- Document element.
- Style reference.
- State reference.

## 4.2 Strict type checking

Invalid type combinations produce errors.

Implicit conversions are prohibited except for explicitly specified safe conversions.

For example, adding a string to a numerical value must not silently convert either operand.

## 4.3 Numerical types

The language supports:

- Integer arithmetic.
- Floating-point arithmetic.
- Fixed-point arithmetic.
- Decimal arithmetic.

The specification must define precision, rounding, overflow and exceptional-value behavior.

Hardware-specific behavior must not silently change document semantics.

Exact numerical widths and decimal formats remain implementation-level parameters to be finalized.

# 6. Mathematical subsystem

The mathematical subsystem is a dedicated part of the unified document model.

It supports mathematical typesetting and bounded evaluation.

## 6.1 Mathematical presentation

The subsystem supports:

- Fractions.
- Superscripts and subscripts.
- Roots.
- Summations.
- Integrals.
- Matrices.
- Piecewise expressions.
- Greek symbols.
- Mathematical operators.
- Scientific notation.
- Aligned equations.

## 6.2 Mathematical evaluation

The bounded expression engine supports:

- Arithmetic.
- Comparisons.
- Trigonometry.
- Logarithms.
- Exponentials.
- Powers and roots.
- Statistics.
- Vectors and matrices.
- Complex numbers.
- Custom bounded functions.

Specialized mathematical operations may be supplied by optional modules.

## 6.3 Execution restrictions

The expression engine does not support arbitrary:

- Loops.
- Recursive execution.
- System calls.
- Filesystem access.
- Network access.
- General-purpose executable code.

Custom functions must be pure, typed and bounded.

All expressions must have defined resource limits.

The initial core implementation defines a deliberately small constant integer
expression subset for rectangle coordinates and dimensions:

```text
@rect(x: 10 + 2 * 3, y: 20, width: 100 / 2, height: 50)
```

It supports signed 64-bit integer literals, unary `+` and `-`, and binary `+`,
`-`, `*`, and `/`. Multiplication and division bind more tightly than addition
and subtraction; parentheses override precedence. Integer division truncates
toward zero. Division by zero and signed overflow are errors. Evaluation is
constant folded while parsing, with limits of 64 nested expression levels and
65,536 operators per document. Variables, floating-point values, units, and
function calls are not part of this initial subset.

# 7. Unified document model

Every document uses one common semantic and rendering model.

Text, equations, tables, images, paths, diagrams and charts can coexist.

The document model supports both flow-based and coordinate-based layout.

## 7.1 Layout types

**Flow layout**

Used for:
- Paragraphs.
- Headings.
- Equations.
- Lists.
- Tables.
- Document sections.

**Canvas layout**

Used for:
- Diagrams.
- Illustrations.
- Technical drawings.
- Charts.
- Precisely positioned content.

Nested layout structures are supported.

## 7.2 Document packaging

Two logical forms are supported:

**Standalone document**

One independently renderable document.

**Document package**

Multiple documents with shared:
- Resources.
- Fonts.
- Images.
- Metadata.
- Supporting datasets.

The package layer is optional and must not be required to interpret a standalone document.

# 8. Element identity and updates

## 8.1 Identifiers

Elements receive identifiers through two mechanisms:

- Automatically generated runtime identifiers.
- Author-defined stable identifiers.

Author-defined IDs are used for persistent references and patches.

Duplicate identifiers are rejected within their defined identity scope.

The current core assigns each element a zero-based source-order index while
executing a document. That index is useful for traversal but is not persistent
identity; only an author-defined identifier is suitable for references or
future patch operations.

## 8.2 Immutable snapshots

Documents are represented as versioned snapshots.

Changes are applied using controlled patches.

Supported operations include:
- Insert.
- Replace.
- Remove.
- Update properties.
- Modify resource references.

## 8.3 Transactional patches

Patch application must be atomic.

If validation fails, the original snapshot remains unchanged.

Patches must include revision information.

Conflicting updates require explicit resolution rather than silently using the last received update.

The renderer should recompute only the affected dependencies.

# 9. Diagnostics and error recovery

The language uses a structured diagnostic system.

## 9.1 Diagnostic fields

A diagnostic may contain:

- Error identifier.
- Severity.
- Source position.
- Element identifier.
- Element type.
- Expected type.
- Actual type.
- Human-readable description.
- Machine-readable recovery context.

## 9.2 Severity levels

- INFO.
- WARNING.
- ERROR.
- FATAL.

## 9.3 Partial rendering

An invalid element must not automatically invalidate the entire document.

Completed valid sections should still render when safe to do so.

An invalid element must not be silently corrected or executed.

The renderer must continue where recovery boundaries permit.

AI systems should be able to consume diagnostics and correct individual sections.

# 10. Graphics and vector drawing

The language is strictly 2D.

It includes a general-purpose vector drawing model.

## 10.1 Core drawing primitives

- Lines.
- Rectangles.
- Rounded rectangles.
- Circles.
- Ellipses.
- Polygons.
- Paths.
- Bézier curves.
- Text paths.
- Groups.
- Transforms.
- Clipping.
- Masks.
- Gradients.
- Patterns.
- Opacity.
- Compositing.

The primitive drawing system must be sufficiently expressive to construct arbitrary 2D illustrations.

The initial prototype draws rectangles, lines, circles, and ellipses. Ellipses
use a center and non-negative horizontal and vertical radii, each bounded by
the coordinate limit.

The initial path syntax accepts uppercase `M`, `L`, `H`, `V`, `C`, `Q`, and
`Z` commands with signed integer coordinates. Each command takes one argument
group; repeated implicit groups, relative commands, arcs, and fractional
coordinates are not yet supported. Path coordinates follow the same range as
other geometry. A path is limited to 64 KiB and 2,048 commands, and execution
accounts for each command against the VM fuel budget.

Groups use the form `@group #optional_id(translate_x, translate_y) { ... }`.
Translations are bounded integer expressions in the local coordinate system.
Nested group translations compose in source order, and group depth is limited
to 64. The VM exposes matching group begin/end events so visitors can preserve
group structure; the SVG backend emits nested `<g>` elements.

## 10.2 Coordinate systems

The rendering model supports:

- Logical coordinates.
- Local coordinates.
- Relative coordinates.
- Nested transformations.
- Physical output units.
- Device scaling.

Transforms must have consistent semantics across backends.

The initial prototype accepts integer positions and endpoints in the range
`-1,000,000` to `1,000,000`, and dimensions and radii from `0` to `1,000,000`.
These limits bound the current SVG renderer's geometry and will be revisited
when the typed length and unit system is implemented.

## 10.3 Graphics rendering

A shared graphics core defines drawing behavior.

Platform-specific backends perform actual rendering.

GPU acceleration is optional.

A CPU fallback must remain available.

GPU acceleration must not silently change logical document semantics.

- Group level.
- Element level.

## 19.3 Event handling

Events use a restricted, declarative action system.

Supported actions may include:
- Updating a state value.
- Selecting an element.
- Changing a permitted property.

The runtime tracks dependencies.

Reactive dependency cycles are rejected unless a future specification explicitly defines a safe bounded mechanism.

State updates are processed through deterministic transactions.

# 23. Resources and security

The language must safely render untrusted documents.

## 23.1 Resource declaration

Resources are explicitly declared.

The runtime receives resources through host-controlled capability handles.

The document does not directly access arbitrary:
- Filesystem paths.
- Network addresses.
- Operating-system resources.

External resources require host authorization.

## 23.2 Resource limits

Limits must exist for:

- Document size.
- Element count.
- Nesting depth.
- Expression complexity.
- Execution time.
- Memory consumption.
- Image dimensions.
- Decoded image memory.
- Animation duration.
- Extension execution.
- Compression and decompression.

Numeric limits will be specified by the runtime profile.

## 23.3 Safety behavior

The runtime must reject unsafe resource requests.

Resource exhaustion must not crash the entire host application.

Untrusted documents must never gain unrestricted code execution.

# 24. Determinism and rendering consistency

The language defines deterministic logical behavior.

The following must have specified semantics:

- Layout.
- Text measurement rules.
- Numerical operations.
- Unit conversions.
- Element ordering.
- Dependency evaluation.
- State updates.

- Deterministic output ordering.

- Incremental invalidation.
- Resource caching.
- Batched drawing.

# 26. Memory management

The implementation uses hybrid memory management.

**Arenas**

Used for temporary parsing and validation allocations.

**Owned resources**

Used for persistent assets.

**Reference counting**

Used for shared resources where appropriate.

**Bounded pools**

Used for frequent rendering-object allocations.

Ownership and lifetime rules must be explicit.

The runtime must avoid ambiguous ownership and uncontrolled allocation.

- Typed document representation.
- Resource table.
- Resource payloads.

# 35. Core and module boundaries

The core must remain small.

Capabilities should be separated into logical modules.

## Mandatory runtime foundation

- Source parsing.
- Type checking.
- Document representation.
- Compact IR.
- Bounded interpreter.
- Diagnostics.
- Core layout.
- Core 2D vector operations.
- Resource capabilities.
- Semantic document information.
- Memory and execution limits.
- Version handling.

## Standard document capabilities

- Text and typography.
- Mathematical typesetting.
- Basic images.
- Tables.
- Basic charts.
- Basic diagrams.
- Styling.
- Accessibility.
- Streaming and patches.

The implementation may package standard capabilities separately while defining their behavior in the language specification.

## Optional modules

- Additional image codecs.
- Specialized scientific charts.
- Advanced diagram layout.
- Additional mathematical functions.
- Animation.
- PDF output.
- Specialized engineering symbols.
- Additional font support.
- Trusted native extensions.

The distinction between core and optional modules is important: the language specification can describe capabilities without requiring every renderer to include every implementation.

# 36. Design invariants

The following rules are foundational and should not be changed casually.

1. Strictly 2D; no native 3D.
2. No arbitrary document-source code execution.
3. No unrestricted filesystem or network access.
4. No unbounded loops or recursion.
5. No ambiguous automatic type conversion.
6. No silent correction of invalid documents.
7. No silent semantic changes between versions.
8. No unbounded resource consumption.
9. No mandatory heavyweight optional subsystem.
10. No platform-specific reinterpretation of document semantics.
11. Stable identifiers for patchable elements.
12. Atomic validation and patch application.
13. Explicit capability handling.
14. Shared document semantics across backends.

### Prototype checkpoint

The current prototype has a first SVG backend exposed by `trytr --render-svg`.
It draws rectangles, lines, circles, ellipses, and the initial path command subset; it
renders heading, text, and math blocks as escaped SVG text. It supports nested
groups with integer translations and computes the SVG viewBox from transformed
geometry. Text uses a simple source-order flow with fixed font sizes and line
spacing; math is displayed as plain text. The generated SVG is bounded to
8 MiB. Clipping, shaped text, and a formal layout model remain future work.

# 38. Decisions still requiring formal implementation-level specification

The architectural direction is established, but these details must not be invented prematurely:

- Language name and file extensions.
- Exact formal grammar and token definitions.
- Exact numeric widths and decimal representation.
- Numeric limits for memory, nesting and execution.
- Exact binary container byte layout.
- Compression algorithms.
- Exact text-shaping and image/PDF libraries.
- Extension ABI details.
- Capability declaration syntax.
- Formal rendering conformance tolerances.
- C23 compiler and platform support matrix.
- Exact serialization and streaming message schemas.

These are specification tasks, not reasons to reopen the foundational design decisions.

# Final project definition

This project is a compact, strict, extensible, C23-based, interpreter-first 2D visual document language.

Its architecture combines a typed declarative document model, a compact execution IR, a bounded interpreter, a deterministic shared rendering core and platform-specific backends.

It supports rich text, mathematics, images, tables, data, charts, diagrams, vector graphics, print, streaming and controlled interactivity.

Its most important engineering constraint is that the mandatory runtime must stay small. Advanced capabilities must be modular, measured and justified.

**The language should be capable of representing very complex visual documents without requiring a complex language runtime.**
